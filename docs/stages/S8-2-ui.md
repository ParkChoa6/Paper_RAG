## 2. 为什么这么写

### 2.1 为什么前端不能直接调库

只要前端能 `from paper_rag.pipeline import ask`，就会出现两条路：
界面一条、API 一条。今天它们一样，改一次就不一样了 ——
而且**分叉那天不会有任何东西报错**，只会出现"界面上是这个数，接口里是那个数"。
这个仓库在 S5-1 / S5-2 上各栽过一次同类问题。

### 2.2 为什么「上次的结果」要存进 `session_state` 再画一遍

Streamlit 的模型很特别：**每次交互（点按钮、拖滑块、勾开关）都会从头重跑整个脚本。**

不存的话会发生这样的事：

```
① 提问 → 渲染答案           ✅
② 用户顺手把 k 从 5 拖到 7    ← 触发重跑
③ 脚本又从头跑一遍，`ask_clicked` 是 False
④ 屏幕空白                  ← 用户以为系统崩了
```

所以结果存进 `st.session_state`，**每次重跑都重画**。
这不是缓存（数据在渲染前的状态），是"这一屏该显示什么"的唯一来源。

⚠️ 副作用要说清楚：调 k 之后，屏幕上仍然是**旧 k 的结果**，只是输入框变了。
所以 `render_result` 会把 `k` 写进耗时那一行 —— 让它自己说出"我是按 k=5 算的"。

### 2.3 为什么重排开关放在侧栏，而且写着代价

`cross-encoder 重排` 默认开。关掉快约 10 倍，但 Top-1 从 68% 掉到 50%。
把这句写进 `help=`，是因为**这是本项目最反直觉的一个取舍**：
慢 10 倍换 18 个点的检索质量。让用户自己拨一次，比读十遍文档有用。

### 2.4 为什么 `parse_failed` 单独一屏

```python
if res["status"] == "parse_failed":
    st.error("模型输出无法解析：...")
    st.markdown("★ 这不是拒答 —— 是管线没产出。")
```

和 S5-10 加 `崩` 那个词是同一条理由：**两者都是 0 分，但病因不同。**
界面上如果都显示"无答案"，下一次有人去修 prompt，而该修的是生成。

## 3. 不应该怎么写

### 3.1 ❌ 在前端"整理"一下结果

比如"没有 problems 就显示 ✓ 引用通过" —— 这是判断，不是展示。
`status` 和 `problems` 的口径只允许有一处定义（`pipeline._judge` / `cite.verify`）。

### 3.2 ❌ 用 `st.cache_data` 缓存 API 结果

Streamlit 的缓存和"同一句话 1 小时内走缓存"是**两层不同的东西**。
前端再缓存一层，用户点了"重新回答"会拿到同一个结果而且**没有提示**。
后端已经有 TTL 缓存，前端不该有第二份真相。

### 3.3 ❌ 把异常当空结果画

`except httpx.HTTPError → st.error(...)` 而不是"画一个空答案"。
"服务没起来"和"模型拒答"在界面上必须长得不一样。

### 4.2 探针抓到的三个真 bug（都是"人眼看不出"的那类）

| 现象 | 病 | 修法 |
|---|---|---|
| 耗时行写「总 433ms（检索 107ms · 生成 1.5s · 校验 0ms）」 | 缓存命中时把**当初那次**的分项抄到了这次 | 按 `cached` 分两支写文案（§2.2） |
| 拖一下 k 滑块，答案从屏幕上消失 | Streamlit 每次交互重跑整个脚本 | 结果进 `session_state`，**每次重跑都重画** |
| 改 k 之后仍是旧结果 | 一度以为缓存键漏了 `k` | 查过：[runtime.py:128](service/runtime.py#L128) 的键里有 `k`。**是探针自己的错** —— 它复用了一个已经被温过的 `k` |

★ 第三条值得单说：**探针也会说谎。**
第 1 遍用 `k=7` 过了；第 2 遍同一个断言红了 —— 因为第 1 遍把 `k=7` 塞进了
服务进程的缓存。断言从"k 生效了吗"变成了"缓存还在吗"，而它看上去一模一样。
改法不是放宽断言，是**换一个没被碰过的 k，并且查材料条数**（条数对不上才是真错）。

### 4.4 ★★ 这一节原本该是个性能结论，结果变成了"我的测量错了"

前端连后端时踩到一个**跟代码无关**的坑：这台机器在 Windows 注册表里配了
系统代理 `127.0.0.1:7900`，而 `httpx` 会把它套到**连 127.0.0.1 的请求**上。

```
    urllib.request.getproxies()
        → {'http': 'http://127.0.0.1:7900', ...}  没有 no_proxy
    httpx.get('http://127.0.0.1:9/x', trust_env=True)   → HTTP 502   ← 代理给的
    httpx.get('http://127.0.0.1:9/x', trust_env=False)  → ConnectError ← 本机真没服务
```

**症状**：后端明明活着，界面报 `502 Bad Gateway`。
那个 502 不是后端给的 —— 是代理给的。而"本机前端 → 本机后端"之间的每一句话，
都要先经过一个第三方进程。

修法是两端都加 `trust_env=False`（`service/ui.py`、`paper_rag/ollama_client.py`），
**但只在回环地址上** —— `OLLAMA_HOST` 指向远程机器时，代理可能正是它能连过去的原因。

#### ★★★ 记一笔：我第一次把这件事写成"快了 5.7 倍"

第一遍量到 `85ms → 15ms`。我据此写进注释："绕代理的代价是 5.7 倍"。

后来按规矩重测三遍（A/B 交替，每遍 15~20 次）：

```
            中位      P90      最大      超过 50ms 的次数
走代理      14.1ms   14.9ms   92.8ms    1 / 20
直连        13.1ms   14.6ms   98.9ms    1 / 20
```

**差 1 毫秒，两边各有一次离群。** 那个"5.7 倍"复现不了 —— 第一次量的
大概是"这台机器当时有多忙"（当时后端在跑重排，CPU 占满）。

★ 一条测量只跑一遍就下结论，量到的往往是噪声。
   注释和本记录里现在写的是**真实理由**：速度不是理由，
   **路径上不该有一个会自己吐 502 的中间人**。这是边界，不是优化。

### 4.5 顺手抽掉了 `make_client` 的两份拷贝（改了这个文件原本的决定）

`llm.py` 末尾原本有一段论证，结论是"两份 `make_client` 是故意的，等第三处出现再抽"。
这一步把它抽成了 `paper_rag/ollama_client.py`，并在原地留下了为什么改主意。

判据换了：

| | 旧 | 新 |
|---|---|---|
| 什么时候该抽 | 重复了第 3 次 | **两份不同步时，有没有东西会报错** |
| 旧的一行代码 | 不同步只是写法丑，行为一样 → 可以等 | |
| 现在带条件的逻辑 | 一份绕代理、一份不绕 → **而耗时差 1ms，不会有人发现** | 不能等了 |

两个模块各自 `re-export`，十几个脚本里的 `from paper_rag.embed import make_client`
一个字没改。改完实测：

```
embed / llm / 新模块 是同一个对象: True
http://localhost:11434     trust_env=False
http://127.0.0.1:11434     trust_env=False
localhost:11434            trust_env=False   ← 手写没带 scheme 的也判对了
http://[::1]:11434         trust_env=False
http://192.168.1.50:11434  trust_env=True    ← 远程保留代理
```

回归：`probe_cite.py` 的 verify 9/9 + repair_indices 8/8，退出码 0；
`ask.py --quiet -k 3` 端到端出了一条带引用校验通过的答案。

### 4.6 `Loading weights:` 那条进度条也关掉了

`scripts/ask.py` 和 uvicorn 的日志里都有一行
`Loading weights: 100%|██████████| 393/393`。它是 **transformers 加载权重**时打的，
和 `rerank.py` 里 `predict(show_progress_bar=False)` 关掉的**不是同一个开关** ——
一个在加载侧，一个在推理侧，同一个毛病。

`rerank._load_model` 里用 `try/finally` 临时关掉、事后还原（这是**全局**状态，
不能因为"我们这里不想看"就把调用方进程里所有进度条永久关掉）。
实测关掉后那一行消失，`is_progress_bar_enabled()` 仍是 `True`。

★ 这个顺带暴露了 S8-1 §4 那张"日志噪音已清"的表**清得不够** ——
  它只清了自己看得见的那两条。**记录里写着"已清"，就该有人去跑一遍确认。**

### 4.7 测到的耗时（同一台机器，不同的忙法）

| 路径 | 耗时 |
|---|---|
| `/api/health` 首屏 | 0.15 ~ 0.42s（启动） |
| 冷的一次（重排，k=5） | 12.0s（模型已在内存） / **29.4s**（模型要现加载） |
| 冷的一次（重排，k=9） | 14.7s |
| 关掉重排（dense，k=9） | 0.9s |
| 缓存命中 | 2ms |

★ 「冷的一次」差了 2.5 倍，不是代码变了：**第一次要把 568M 的重排权重从磁盘读进来**
（`Loading weights: 393/393`），第二次就不用。所以看这个数必须先问
「重排模型这会儿在内存里吗」。表里两个数都留着，就是为了不被其中一个骗。

★ 这也是界面侧栏那句 `启动耗时` 的意义：它说的是**装配**用了多久（0.15s），
  不是"第一次问一句要多久"。两件事分开报，才不会互相顶替。

## 5. 你要补的概念

### 5.1 Streamlit 的执行模型

**脚本每次交互都从头跑一遍。** 这一条解释了这个框架的几乎所有怪现象：
为什么状态要放 `session_state`、为什么 `st.form` 存在、
为什么"在脚本里直接 `while True`"是灾难。

### 5.2 前端的「唯一真相」原则

界面上的每一个数，都必须能追到 API 返回的某个字段。
追不到的数 = 前端自己算的 = 迟早和生产不一致。

（例外：`elapsed` —— 前端自己掐的表，量的是"用户等了多久"，
 包括网络和排队。它和 `timings.total` 是**两个不同的量**，所以缓存命中时
 两个都要出现，而且要写清楚哪个是哪个。见 §2.2。）

### 5.3 本机回环 ≠ 不走代理

`trust_env=True` 的意思是"读环境里的代理设置"，而 Windows 的"环境"里
还有**注册表**（`urllib.request.getproxies()` 会读它）。
一份"连 127.0.0.1"的请求，照样会被塞进 `127.0.0.1:7900` 那个代理。

判断"到底走没走代理"的可靠办法不是看配置，是**打一个必然没有服务的端口**，
看错误是「404/502 有东西应答」还是「目标计算机积极拒绝」。
后者才是"真的直连"。

### 5.4 一次测量不是测量

`85ms → 15ms` 和 `14ms → 13ms` 都是这台机器上量出来的，相隔不到一小时。
差的是**当时机器有多忙**，不是代码。

要下"快了多少"的结论，至少：A/B 交替（避免机器越来越忙）、
看中位数和 P90 而不只看均值（尾延迟才是用户感觉到的东西）、连跑三遍。
**如果三遍的结论不一样，那就没有结论。**

## 7. 遗留

- 没有多轮对话（每个问题独立）。
- 没有历史列表（刷新即丢）。
- 窄屏（手机）没有专门适配 —— 这是本机演示工具，不是产品。
- `probe_embed.py` / `probe_similarity.py` 还在自己 `ollama.Client(host=...)`，
  没走 `ollama_client.make_client` —— 这两个是一次性探针，仍然是"会绕代理"的。
  哪天要复用它们，先改成 import。
- 探针只按了「提问」这一条主路径。**拒答**（🤷）、**可疑**（⚠️）、
  **解析失败**（💥）三种判定没有各自的断言 —— 它们要构造特定的后端返回，
  AppTest 造不出来（它跑的是真的 ui.py，对着真的后端）。
  真要测，得给探针加一个"假后端"（`POLICY` 见 §2.4），本步没做。
