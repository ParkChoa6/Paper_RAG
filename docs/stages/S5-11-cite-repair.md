## 2. 为什么这么写

### 2.1 为什么这件事能由代码做

> **编号不是证据，原文才是。**

`quotes` 里那句英文原句是模型从材料里抄出来的 —— S5-8 已经量过：
684 条 quote 里只有 2 条是全库都找不到的真伪造。
既然原句是真的，那"它到底出自哪条材料"就是一个**可以由代码算出来的量**：
拿这句话到本次的 k 条材料里逐条搜一遍。

S5-8 §7.4 提的两个方向是"让模型先写句子再贴编号"和"要求 quotes 带原文片段以便反查"。
第二个方向其实**已经满足了** —— quotes 本来就是原文片段。缺的只是没人去反查。

★ 这和 `parse_response` 那条「凡是需要你补一个值的，就是在编」是同一条原则的两面：
**能由代码确定的，别让模型猜。**

### 2.2 为什么不在 `verify` 里修

`verify` 的职责是**报告真伪**。一个既当裁判又当修理工的校验器，
改完之后永远报"没问题" —— 你会失去「模型有多爱贴错编号」这个数，
而那正是 S5-8 花一整步拆出来的东西。

所以：**修在 `repair_indices`，验在 `verify`，两条路径各自可测。**
`verify` 的 9 关离线测试一个字没动，全部照旧通过。

### 2.3 为什么修了必须说（`repairs` 字段）

静默修 = 把"模型的错"从数据里抹掉。
本项目最忌讳的一种"改对了"就是这种：**看起来对了，但原因消失了。**

所以 `repair_indices` 返回第二项，`pipeline.ask` 原样透传，
CLI 打印它，评测逐行记 `n_repairs`，判卷表标签上也写出来。
★ `n_repairs` 是**模型犯错的计数**，不是"系统更好了"的证据 ——
problem 数变少的同时，这个数会变多。两列必须一起看。

### 2.4 为什么正文里的 `[n]` 也要一起改

只改 `quotes` 的键不改 `answer` 正文，交付出去的回答仍然写着 `[1]`，
而下面列的是材料 3 的原文 —— 那只是**把矛盾藏进了两个字段之间**。

所以 `_MARKER_RE_TEXT` 会扫 `answer` 里的 `[n]`，**只替换被纠正过的那些**。
`[94]`（论文自己的参考文献编号）不在映射里，原样不动。

### 2.5 边界：宁可不修

| 情况 | 处理 | 理由 |
|---|---|---|
| 原句在 0 条材料里找到 | 不动 | 真伪造，不是编号问题 |
| 原句在 ≥2 条材料里都能找到 | 不动 | 归属有歧义，猜就是编 |
| 纠正后两条引用撞到同一份材料 | **整批不动** | 至少有一条没纠正对 |
| 拒答（`used=[]`） | 不动 | 没有编号可言 |
| 编号越界（>k） | 不动 | 交给 `verify` 的 ① 报 |

★ 撞车那条**不往 `repairs` 里塞一句"我想修但没修"**：
`repairs` 的语义是"改过了"。塞进去会让 `n_repairs` 变成两种东西的和，
而"修了 3 处"和"3 处想修没修"在报表上长得一模一样。
没修的，`verify` 那边本来就会如实报出来。

## 3. 不应该怎么写

### 3.1 ❌ 在 `verify` 里直接改 `parsed`

校验器一旦有写权限，你就再也量不到"模型原本错了几处"。
S5-8 拆出来的那 8 条会重新变成 0 条 —— 不是修好了，是**看不见了**。

### 3.2 ❌ 让模型"重新检查一遍编号"

多一次模型调用 = 多 3 秒 + 多一种失败模式，而且它可能又错一次。
**代码能算的，不要问模型。**

### 3.3 ❌ 用 `difflib` 找"最像的材料"

`difflib` 永远会给你一个"最像"的答案 —— 包括原句根本不存在的时候。
那等于把"0 条候选"变成了"1 条候选"，所有真伪造都会被修成别的东西。
S5-8 §3.2 已经拒绝过模糊匹配，这里同一个理由。

### 3.4 ❌ 只测"改完之后还剩几条不匹配"

那测不出"改错了"：把所有编号都改成 1，剩下的不匹配数也会下降。
离线关卡必须同时看 **used / quotes 键 / answer 正文 / 修了几处** 四样。

## 4. 怎么验证它真的对了

### 4.1 离线关卡 8/8（构造输入，不调模型）

```
✅ 全部对得上            没事可修的时候不许乱改
✅ 单条错配              原句来自材料 3，编号和正文一起改
✅ 两条互换              同时替换，不能先改一个再改另一个
✅ 真伪造不动            哪儿都找不到 = 编造，不是编号问题
✅ 原句两处都有 → 不动    归属不唯一时宁可不修，交给 verify 报
✅ 纠正后撞车 → 整批不动   两条引用指到同一份材料
✅ 拒答不动              没有编号可言
✅ 正文里的 [94] 不动     只改被纠正过的编号
```

★ 「两条互换」这一关是**唯一**能钉住"同时替换"的：先改 1→3 再改 3→1，
会把第一条改出来的 3 又改回 1（或反之），两条都错。

### 4.4 剩下的是同一段原文被贴给了两个编号

历史回放剩下的 9 处，全部长这样：


## 5. 你要补的概念

### 5.1 「可推导值」与「模型自由生成值」

一个字段，如果代码能从别的字段算出来，那就不该让模型生成。
让模型生成 = 引入一类**本不存在的**错误，还多一层解析风险。

判断方法：**"这个值的真值，除了模型还有谁知道？"**
- `answer` 的措辞：只有模型知道 → 必须生成。
- 引用出自哪条材料：原文里有，代码能搜到 → **可推导**。

### 5.2 修复的可观测性

自动修复的危险不在于"修错"，而在于**修对了却没人知道曾经错过**。
所以任何自动修正都必须：① 计数；② 列出改了什么；③ 和"原始错误数"分开记。

### 5.3 宁可不修 > 猜着修

系统的可信度来自"不修的时候它也不装作修好了"。
`repair_indices` 在 9/26 的情况下选择不动 —— 这不是能力不足，是**设计**。

## 7. 遗留 / 下一步

### 7.1 同一段被重复引用（9/26）没修

需要先定语义：合并 `used`？还是允许两条引用指向同一材料？
定之前不动。

### 7.2 `verify` 的返回值还是字符串

`repair_indices` 需要结构化的"哪条属于哪条"，现在是自己重新算一遍
（和 `verify` 里 ④ 的算法一样，但两份实现）。
S5-8 §2.5 记过这笔技术债，本步让它**又长了一寸**。
下次改 `verify` 的判据时，两边必须同时改 —— 这是明摆着的隐患。

### 7.3 修完之后没有重跑判卷

`repairs` 只改编号不改答案内容，所以答对率理论上不变。
但"引用校验通过率"会变 —— 那个数要等下一次端到端评测才更新。
