## 1. 改了什么

### 1.1 判卷表填完（84/84）

`data/processed/e2e_judge.md` 里 84 个 `判定 甲：____` 全部填上。
判卷依据、逐格理由留在 `data/processed/e2e_judge_verdicts.json`（非「对」的格子都带一句为什么）。

### 1.2 ★ 判定词表加了第 6 个词：`崩`

原来只有 5 个词（对/错/缺/拒/编）。但 `pipeline.ask()` 有 **4 个 status**，
其中 `refused`（契约性拒答）和 `parse_failed`（压根没交付）在
`pipeline.ask` 的 docstring 里**明确写了不许合并**。

判卷表只有 5 个词 → `parse_failed` 无处可去 → 只能塞进「缺」。
于是**「该答没答」（判断失误）和「没输出」（管线故障）在最后一步被压成同一个数**。

> 这正是 S5-7 花了一整步去修的那类病。不能又在判卷这一步把它糊回去。

新词：`崩 = 没交付（parse_failed / 空回答）—— 管线没产出，不是拒答`。

### 1.3 `score_judge.py` / `eval_answer.py` 同步

- `score_judge.py`：`VERDICTS` 加 `崩`，统计表多一列，表尾说明同步。
- `eval_answer.py`：判卷表表头加一行 `崩` 的定义（两边不同步 = 表上说崩、算分说不认识）。

## 2. 为什么这么写

### 2.1 为什么 `崩` 必须单独一个词

答对率的分母是 28，`崩` 和 `缺` 都不进分子 —— 从**数字上**看它们一样，
所以很容易觉得"合并也无所谓"。

> **数字一样，病因不一样。**
> `缺` 说明检索到了、模型也答得出来，但它选择了不答 —— 修 prompt 或修拒答判据。
> `崩` 说明模型输出根本没解析成 JSON —— 修生成（S5-7 就是这么修的）。
> 合并之后，「dense 在这道题上丢了 1 分」这句话的**原因**就消失了。

★ 而且它马上就用上了：dense 臂的 3 个 `崩` **正好**是 S5-6 记录里
已知会被 S5-7 修掉的那三题（Q6 / Q13 / Q24）。见 §4.3。

### 2.2 为什么这次由**模型**判卷，以及怎么标

S5-6 §4.8 写着「判卷必须人来做」。这一步的判卷**是我（Claude）做的**，
不是出题人做的。记录里必须把这句写清楚，因为它决定了结论的强度：

| | 人工判卷 | 本步 |
|---|---|---|
| 盲法 | ✅ 甲/乙/丙 打乱 | ✅ 同一张盲表 |
| 判卷人和模型不同源 | ✅ | ✅（qwen2:7b 生成，Claude 判） |
| 判卷人没有立场偏好 | 需要自律 | ⚠️ **无法自证** |
| 可复核 | 只有本人 | ✅ 逐格理由落盘 |
| 成本 | 84 格 × 人 | 一次性 |

**所以：这批数字可以当"第一版阅读"，不能当"最终审计"。**
用户抽检的 10 格见 §4.4 —— 如果抽检推翻 ≥3 格，整张表要重判。

### 2.3 为什么「判定」栏不看引用问题

表头给每个 arm 标了「｜引用有问题」。判卷时**故意不拿它当证据**：

- 一条引文标了「疑似伪造」，答案本身可能完全正确 —— 那是引用栏的事；
- 反过来，引用校验全过，答案也可能是错的（它抄对了原文，但答非所问）。

两个轴，两个数。S5-8 已经量过：把「编号错配」混进「引用有问题」里，
会让人拿着"模型会编引用"的结论去修一个不存在的病。

## 3. 不应该怎么写

### 3.1 ❌ 把 `parse_failed` 判成 `缺`

见 §2.1。这是本次**唯一**一个"表结构改了一点"的地方，因为它是最容易被糊掉的格子。

### 3.2 ❌ 判完先看 `e2e_key.json` 再回头改判定

盲表的意义在于：你判 Q3 的时候不知道哪条是 dense。
揭盲之后再"调整"任何一个格子，等于把结果往你预期的方向拧。

### 3.3 ❌ 拿 21 个点的差当结论

n=28，80% 附近 95% 区间约 ±15 点。p=0.114 ≥ 0.05 —— **没有证据表明两臂答对率不同**。
能说的只有："方向上和检索层的 +18 点一致，而中间指标（合规回答率）看不到这个差"。

### 3.4 ❌ 顺手把 S5-6 的「合规回答」那一列删了

它没坏。坏的是**把它当出口指标用**。两列并排看，才知道中间指标吃了什么。

## 4. 怎么验证它真的对了

### 4.1 ★★★ 结果（S5-6 那一次运行的判卷表）

```
arm            对     错     缺     拒     编     崩    答对率
-------------------------------------------------------------
dense         18     3     0     2     2     3    18/28 = 64%
oracle        26     1     0     0     0     1    26/28 = 93%
rerank        24     2     1     1     0     0    24/28 = 86%
```

```
★ 配对 McNemar：dense 64% → rerank 86%（差 +21 点，28 题）
  只有 rerank 对：8 题（Q3 Q6 Q9 Q12 Q17 Q18 Q24 Q26）
  只有 dense 对：2 题（Q7 Q10）
  p = 0.114   ≥ 0.05 → 没有证据表明两臂答对率不同
```

### 4.2 ★★ 和中间指标并排看 —— 这张表是本步最重要的产出

| 指标 | dense | rerank | 差 |
|---|---|---|---|
| 材料含答案（检索层） | 71% | 89% | **+18 点** |
| 合规回答（中间指标） | 79% | 79% | **0 点** |
| **答对率（出口指标）** | **64%** | **86%** | **+21 点** |

S5-6 的结论是「检索涨了 18 点，答案质量一点没动 —— 瓶颈在生成层」。
判卷表把这句话**改了**：

> 答案质量**动了**，只是中间指标没接住。
> 「合规回答率」量的是"有没有交付一个有据可查的答案"，它对本步最关心的
> **"答得对不对"** 没有分辨率 —— 一个编得很像的错答案，和一个对的答案，
> 在那一列里长得一模一样。

★ 这正是 S5-6 §5.1 讲的「中间指标 vs 出口指标」，只不过当时的结论是
**基于中间指标**下的。等出口指标真的量出来，结论反了。

⚠️ 但仍然**不能说**"检索层 +18 点导致答对率 +21 点"：
p=0.114，且下面 §4.3 有一个实打实的混淆。

## 5. 你要补的概念

### 5.1 出口指标 vs 中间指标（这次是本步最贵的一课）

中间指标（proxy）是"能自动算、且**相信**它和真目标相关"的量。
它便宜，所以一旦建立就会一直用 —— 而它**可能在很久以后才被证伪**。

本步之前：合规回答率 79% vs 79% → 结论"检索改进没传导到答案"。
本步之后：答对率 64% vs 86% → 结论"传导了，但中间指标看不见"。

★ 判据不是"中间指标高了就是好"，而是：**每隔一段时间，用出口指标校准一次中间指标**。
本步就是那次校准。

### 5.2 判定词表就是一种 schema

加一个词、少一个词，会改变下游所有数字的含义。
本步加 `崩` 的成本是 3 行代码，收益是"差异有了原因"。
**schema 变更必须同时改：生成端的表头、算分端的词表、记录里的口径。**

### 5.3 McNemar 在 n=28 上能说什么

配对检验比"两组比例"更敏感，因为同一道题在两个配置下的难度被抵消了。
但 n=28 时，`b+c=10` 的样本量下 p 仍然到不了 0.05 ——
所以正确的说法是"没有证据表明不同"，**不是**"相同"。
（区别在于：前者允许你下次用更大的样本再测一次。）
